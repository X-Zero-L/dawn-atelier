# ADR-0001：按适配器复用本地存档编辑流程

状态：接受

## 背景

黎明工坊已经拥有《黎明门前的吹笛人》的编辑界面、预设、存档保护、资源准备和桌面更新能力。`web_server.py` 同时承担 HTTP、游戏字段展示、修改规则和写入协调；`piper_save.py` 的备份目录来自全局配置。直接复制这些入口来适配另一款游戏，会连同现有游戏的路径、格式和规则一起复制。

不同游戏共享“读取、预览、备份、提交”的顺序，但不共享金币编码、物品记录或解锁方式。首轮提取需要覆盖两种真实存在的格式实现：现有游戏格式和明确标为合成数据的参考 JSON 格式。

## 决定

新增不依赖游戏资源的 `atelier` Module，通过 `Adapter` Interface 接入各游戏。该 Seam 接收明确注册的 Adapter；首版不扫描目录加载任意插件代码，不下载第三方适配器。

通用 Module 包含快照、计划标识、提交前复核、备份、暂存回读及导出或替换。Adapter 包含格式识别、字段语义、操作执行、结果校验、兼容证据和运行状态检查。适配器验证失败时，通用流程不能继续写入。

《黎明门前的吹笛人》继续使用现有编解码、物品、好感和进阶规则。已有桌面界面、数据路径和下载入口保留，通过受控接入逐步使用通用流程，避免同一轮同时更换领域逻辑、窗口框架和更新机制。

`json-reference` 使用专用合成格式标记，承担第二个 Adapter 和开发示例的作用。它不能读取任意 JSON 存档，也不表示已经支持另一款商业游戏。合成参考适配器只开放导出。

### 提交约束

1. 快照捕获原始字节；预览和提交共享该快照。
2. 计划由适配器生成，包含明确操作和修改结果；预览阶段不写源存档。
3. 提交要求当前计划标识，并重新核对源内容、适配器兼容状态及目标写入方式。
4. 先创建原档备份，再写暂存文件；回读暂存内容并再次确认源文件没有改变后完成写入。
5. 写入范围由目标模式决定：导出不覆盖已有输出，应用只替换源文件。
6. 错误不能被当作成功。操作记录区分备份、输出与校验状态，不能将备份已创建等同于存档已保存。

计划标识用于一致性检查，不是签名或权限系统。适配器代码作为本地受信任代码运行；首版没有插件沙箱。

### 兼容性约束

版本判断留在 Adapter。对《黎明门前的吹笛人》，已核对的二进制可直接匹配配置；未知补丁需满足存档结构、配置定义和对应序列化证据。资源准备完成后记录当前安装，游戏更新会使旧准备结果和待提交计划失效。

序列化字节指纹对编译器重排较敏感，这是允许写入前的保守检查。仅比较版本日期、字段名称或某个存档能够解析，均不足以取消该检查。

### 数据隔离

新游戏使用自己的稳定游戏 ID 与工作目录。跨游戏不能共用准备完成标记、备份、导出、草稿或自定义方案。现有游戏保留既有 `data/game` 与 `data/demo` 路径，避免升级时移动用户数据。后续迁移需要单独设计和验证。

## 考虑过的方案

| 方案 | 取舍 |
| --- | --- |
| 为每款游戏复制整个编辑器 | 写入保护、桌面更新和回归检查会分叉，修复难以同步。 |
| 只把字段路径和文件后缀配置化 | 无法表达资源派生上限、关联字段、物品记录和原生解锁条件。 |
| 首轮改成任意插件市场与统一动态 GUI | 引入签名、兼容版本、代码信任和控件协议，当前两种格式不需要这些复杂度。 |
| 让存档和实时内存修改共用同一写入流程 | 内存修改没有相同的文件快照、持久备份和原子替换语义，应由后续独立契约承载。 |

## 结果与后续条件

共享模块集中处理重复且容易出错的提交逻辑；适配器保留领域知识的 Locality。第二个格式让 Interface 有可运行的对照实现，新增游戏可以复用提交流程而不依赖当前游戏安装。

现有玩家界面仍包含《黎明门前的吹笛人》的专用视图。注册一个新适配器不会自动生成背包、角色和解锁界面。未来需要另一个实际游戏时，再从它的交互需求提取通用控件协议。

实时内存功能只作为后续扩展方向：需要独立的进程身份、地址解析、读取一致性、写入验证和撤销策略。当前发布不提供这项能力，也不把存档测试用作内存修改的完成证据。
