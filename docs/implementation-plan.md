# 多游戏框架实施计划

## 目标与范围

将已有存档修改流程中的快照、预览、校验、备份与写入抽为可复用模块，同时继续维护《黎明门前的吹笛人》的界面、预设、游戏更新检测与桌面更新。第二个适配器使用自定义的合成 JSON 格式，证明框架可以处理不同存档格式；它不代表支持第二款商业游戏。

## 改动顺序

1. **记录当前行为。** 保留现有好感、进阶准备、存档刷新、兼容性和桌面更新检查；补充框架契约的回归验证，覆盖过期快照、变更后的计划、备份失败与未知格式拒绝写入。
2. **提取通用写入模块。** 将备份目录作为参数，集中处理源文件复核、独占创建备份、暂存回读与替换。旧调用入口委托新实现，保留现有路径和返回格式。
3. **定义适配器与编辑流程。** 接入游戏描述、能力、快照、计划、兼容判断和运行状态；计划绑定原始存档与操作，提交前重新验证。
4. **接入两个格式。** 《黎明门前的吹笛人》复用已确认的编解码与游戏规则；合成 JSON 适配器拥有独立格式标记、严格操作白名单和独立备份目录。
5. **提供开发入口。** 通过 CLI 列出适配器、读取存档、生成预览、导出与应用，提供新适配器骨架和文档。前端显示实际游戏能力与状态。
6. **更新本机新版本适配。** 从当前安装提取结构证据，确认字段编号、类型、编码和序列化逻辑；必要时新增兼容配置。支持判定依据证据，不单凭版本日期。
7. **验证与发布。** 运行针对性回归、现有回归与构建检查；检查打包资源白名单和变更后的媒体。按逻辑分组提交，公开说明已实现功能与尚未实现的扩展。

## 必须保持的行为

- 编辑预览不写真实存档；两种写入模式都先备份。
- 游戏重新保存后，旧计划失效；旧草稿可保留，但不能自动套用到新进度。
- 源文件、游戏安装或计划内容改变时，先重新读取并生成预览。
- 不了解的字段按对应编解码器的规则保留；未经证据确认的格式不开放写入。
- 炼金解锁与工坊升级继续补齐条件，由游戏执行解锁和升级；数值满好感不表示剧情完成。
- 真实游戏存档、解包资源、二进制、密钥和本机配置不进入仓库或发布包。
- 框架不新增依赖。首版不包含动态下载插件、实时内存修改或通用游戏规则猜测。

## 完成证据

实现和检查结果以对应提交及发布记录为准。本文件记录实施范围和顺序，不将计划中的能力视为已经验证完成。框架使用方式与当前范围见 [框架开发指南](framework.md)，设计约束见 [ADR-0001](adr/0001-game-adapters.md)。
